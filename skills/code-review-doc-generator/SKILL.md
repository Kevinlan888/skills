# Code Review Document Generator

自动化代码评审文档生成技能，支持 Git/SVN 双版本控制系统。在同一对话内完成首次和二次评审的完整闭环，用户确认后生成带多维效率指标的结构化评审文档。

## 核心设计理念

此工作流的核心价值在于 **量化 AI 评审效率**。相比人工评审，AI 评审的提效比例（代码评审提效）是衡量价值的核心指标。整个流程围绕"检测 → 提问 → 评审 → 迭代 → 生成 → 校验"六个阶段展开。

工作流区分两类评审场景：
- **类型 A（变更类）**：基于 VCS diff 的变更评审，需要交互提问收集元信息
- **类型 B（片段类）**：用户直接提供的代码片段/文件评审，跳过提问直接评审

> **📁 配套资源：** 文档模板在 `references/templates.md`，项目类型映射在 `references/project-mapping.md`，效率指标计算方法在 `references/metrics-guide.md`，YAML 校验脚本在 `scripts/validate_yaml.py`。

---

## 状态机（核心流程）

```
[INIT] → [DETECTED] → [QUESTIONED? 仅类型A] → [REVIEWING] → [COMPLETED]
```

关键约束：
- 类型 A 必须经过 QUESTIONED 状态（等待用户回答），禁止跳过
- 类型 B 从 DETECTED 直接到 REVIEWING
- 所有阶段 **静默执行**（不输出"正在检测"、"正在评审"等过程文字），仅在需要用户交互时输出固定模板
- 进入 COMPLETED 后立即生成文档，**禁止二次确认**"是否生成文档"

---

## Phase 0: 评审类型识别 (🔇 静默)

分析用户请求，判断评审类型，不输出任何过程信息。

**类型 A — 变更类评审：**
- Git 暂存区/工作区变更、commit diff、SVN 工作区修改
- 用户提及"变更"、"修改"、"提交"、"diff"、"stage" 等关键词

**类型 B — 代码片段类评审：**
- 用户直接粘贴代码、指定评审特定函数/文件
- 评审对象已在对话上下文中（当前打开文件/选中代码）
- 用户提及"函数"、"方法"、"这段代码"、"这个文件" 等关键词

默认规则：无法判断时按类型 A 处理。

## Phase 1: 环境检测与初始化 (🔇 静默)

> 详细的项目类型映射和 VCS 命令见 `references/project-mapping.md`。

### 1.1 VCS 检测

按顺序检测 `.git` → `.svn`，两者都不存在时提示用户切换到项目根目录。

### 1.2 发起人信息

- **Git**：`git config user.name` / `git config user.email`
- **SVN**：`svn auth` 或 `svn log -l 1 --quiet`
- 获取失败时在 Phase 2 提问中补充询问

### 1.3 项目类型识别

读取 `references/project-mapping.md` 中的映射表，按 Git Remote URL → SVN URL → AI 推断的顺序识别项目类型（候选：2D客户端、2DSDK、3D线激光客户端/SDK、3D双目客户端/SDK、智能机、视觉工具、测开、其他）。

### 1.4 模块名称

根据文件路径、commit message、代码功能智能推断，在提问时展示给用户确认。

## Phase 2: 合并提问

**类型 A 必须执行，类型 B 自动跳过。**

### 类型 A 输出模板（逐字输出，禁止修改）

```
📋 请先填写以下信息，然后开始评审

请复制以下模板填写后回复：

项目模块：{项目分类}-{功能模块}（自动生成，可修改）

是否AI辅助：是/否

AI开发耗时：___小时

其他说明：（选填）
```

回答中的"项目模块"决定文档标题，"是否AI辅助"和"AI开发耗时"决定是否计算开发效率指标。必须等待用户真实回复，禁止假设或自动填充。

### 类型 B 默认值

类型 B 自动使用 `AI辅助=否`，`AI开发耗时=不适用`，直接进入 Phase 3。

## Phase 3: 代码评审

### 3.1 获取变更 (🔇 静默)

**Git：**
```bash
git diff --cached --name-only
git diff --cached --shortstat
git diff --cached
```

**SVN：**
```bash
svn status
svn diff
```

### 3.2 评审维度

覆盖六个维度：代码规范性、潜在 Bug 和风险、性能问题、安全隐患、可维护性、最佳实践。

### 3.3 评审结果展示模板

```
【首次评审结果】

变更概览：{files}个文件，+{add}/-{del}行

### 严重问题 ({count})
1. {问题标题} - `{文件}:{行号}`

### 主要问题 ({count})
...

### 次要问题 ({count})
...

### 改进建议 ({count})
...
```

## Phase 4: 评审循环

### 4.1 评审后询问（逐字输出）

```
评审结果已展示，请选择下一步操作：

1. 不再修改，生成最终文档
2. 已修改代码，请再次评审
3. 取消评审

请回复数字（1/2/3）：
```

处理逻辑：
- **选 1**：立即进入 Phase 5 生成文档
- **选 2**：静默执行 `git diff` / `svn diff` 获取最新变更，对比首次问题分析修复状态（已修复/部分修复/未修复/新增），展示二次评审结果
- **选 3**：结束流程，不生成文档

### 4.2 二次评审结果展示

```
【二次评审结果】

### 采纳情况分析
| 首次问题 | 状态 | 备注 |
|---------|------|------|
| 问题1: ... | ✅ 已修复 | - |
| 问题2: ... | ⚠️ 部分修复 | 仍需处理... |
| 问题3: ... | ❌ 未修复 | - |

### 新发现问题
...
```

### 4.3 二次评审后询问

```
二次评审结果已展示，请选择下一步操作：

1. 不再修改，生成最终文档
2. 已修改代码，请再次评审
3. 取消评审

请回复数字（1/2/3）：
```

## Phase 5: 生成文档

> 进入此阶段后 **立即生成文档**，禁止询问"是否生成"或"确认生成"。

### 5.1 文档结构

从 `references/templates.md` 读取完整的 YAML frontmatter 和 Markdown 正文模板。文档由两部分组成：

1. **YAML frontmatter**：结构化元数据，包含评审ID、评审人、变更统计、多维效率指标、问题记录
2. **Markdown 正文**：人类可读的评审报告，包含变更概览、问题清单、效率指标表格

### 5.2 效率指标计算

从 `references/metrics-guide.md` 读取计算公式和估算标准。核心指标：

```
代码评审提效 = (预估人工评审耗时 - AI评审耗时) / 预估人工评审耗时 × 100%
问题密度 = AI问题摘出数 / 代码总行数 × 100
已采纳问题率 = 已采纳问题数 / 首次发现问题总数 × 100%
```

- 人工耗时根据变更规模（small/medium/large/xlarge）估算
- 代码质量评分（复杂度/可维护性/安全性）1-10 分
- `is_ai_assisted=true` 时额外计算开发效率指标

### 5.3 文件命名与存储

```
目录：Review/
命名：Review/{项目}_AI代码评审_{评审人}.md
```

文件名为固定的三部分结构，禁止添加模块名、函数名、评审轮次等后缀。

### 5.4 最终输出（逐字输出）

```
📄 评审文档已生成

文档路径：Review/{项目}_AI代码评审_{评审人}.md
```

---

## Phase 6: YAML 校验 (🔇 静默)

文档生成后，**必须**运行 YAML 校验脚本确保输出质量：

```bash
python scripts/validate_yaml.py Review/{项目}_AI代码评审_{评审人}.md
```

如果校验不通过，根据错误提示修正文档中的 YAML 字段后重新校验，直到通过为止。校验脚本会检查：
- 所有必填字段是否存在
- 字段类型和取值范围（如 quality scores 必须 1-10）
- 枚举值合法性（severity、status、change_size 等）
- 文件名命名规范
- 数值一致性（如 total = critical + major + minor + suggestion）

## 静默执行原则

以下阶段 **不向用户输出任何过程信息**，仅在出错时报错：

- Phase 0：类型识别
- Phase 1：VCS 检测、用户信息获取、项目类型识别
- Phase 3.1：diff 命令执行
- Phase 4.2：二次评审的 diff 获取和评审执行
- Phase 5：指标计算、模板填充、文件写入
- Phase 6：YAML 校验脚本执行（校验通过时不输出，仅在失败时报告错误）

这样做是为了保持交互简洁——用户只看到关键决策点和最终结果，不被过程噪音干扰。

---

## 错误处理

| 场景 | 处理方式 |
|-----|---------|
| 非项目目录（无 .git/.svn） | 提示切换到项目根目录 |
| 无代码变更 | 提示暂存区/工作区无变更 |
| 获取用户信息失败 | 在 Phase 2 提问中增加"评审人"字段 |
| 用户选择"取消评审" | 结束流程，不生成文档 |
| YAML 校验失败 | 根据错误提示修正后重新校验 |
